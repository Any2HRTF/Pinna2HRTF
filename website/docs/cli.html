The Python CLI

Use the CLI to prepare scans, run optional Mesh2PPM inference, set up and solve simulations, and process the results. Run stages one at a time, or describe a full run in YAML.

Written for version 2.0. The current download is v1.1.0, so a few things may look different in your copy.

Install the Python environment

Install Git and uv, then clone the repository and create the locked Python 3.11 environment:

git clone https://github.com/Any2HRTF/Pinna2HRTF.git
cd Pinna2HRTF
uv sync --locked --python 3.11

Prepare the external native tools once:

# macOS or Linux
bash Scripts/prepare_external_tools.sh
# Windows PowerShell
.\Scripts\prepare_windows_external_tools.ps1

The setup scripts download and build native dependencies. macOS requires Xcode Command Line Tools. Linux requires a C/C++ toolchain, Make, and the system libraries needed by Blender bpy. The Windows script installs MSYS2 if it is not already available.

For help, run uv run Pinna2HRTF --help or add --help to a subcommand.

Available stages

Configure a run

Create a complete configuration template:

uv run Pinna2HRTF run-config --write-template pinna2hrtf.yaml

Edit input paths, output directory, external tool locations, evaluation grid, frequency range, and stage settings. Relative paths are resolved from the YAML file’s directory. If paths.output_dir is omitted, outputs are written next to the YAML file. Set an unused ear to null. Mesh2PPM inference is disabled in the template, and preprocessing uses original meshes unless inference.use_predictions_for_preprocessing is set to true.

Inspect the planned run first:

uv run Pinna2HRTF run-config --config pinna2hrtf.yaml --stage all --dry-run

Then run all enabled stages, or run a single stage:

uv run Pinna2HRTF run-config --config pinna2hrtf.yaml --stage all
uv run Pinna2HRTF preprocessing --config pinna2hrtf.yaml
uv run Pinna2HRTF numcalc --config pinna2hrtf.yaml

Run multiple selected stages by repeating --stage. An explicitly selected stage runs even when its YAML enabled value is false. Add --dry-run to inspect a config-based run without executing the stages or changing any file. YAML runs write left and right simulation projects under Projects/Left and Projects/Right in the output folder.

Config-based SOFA export checks the meshes, grid, and settings that preprocessing recorded, and stops if they no longer match. Older projects without this record still export, with a warning. Standalone sofa conversion uses the simulation project parameters and validates their HRIR frequency vector.

Inference records the ear mesh, model, settings and prediction of each ear in .pinna2hrtf-inference-receipt.json. With inference.use_predictions_for_preprocessing: true, preprocessing stops with error StageNotCurrent before writing anything if a selected ear’s prediction no longer matches that record. Predictions from older versions have no such record and are not used. Run inference again, or set use_predictions_for_preprocessing: false to preprocess the original meshes.

Preprocessing records its inputs and the generated parameters.json, NumCalc/source_*/NC.inp, ObjectMeshes and EvaluationGrids files of each ear in .pinna2hrtf-preprocessing-inputs-v1.json after the projects are in place. Preprocessing is reported as current only while those files are present and unchanged.

Head shape

Preprocessing builds an ellipsoidal dummy head around the ears. Its ear-to-ear radius comes from the ear meshes and is multiplied by preprocessing.head_radius_scale (default 1.01). head_width_scale (front to back, 1.5) and head_height_scale (1.5) are relative to that radius. head_y_deformation (0) changes the ear-to-ear width with height, per millimetre: positive values widen the head above the ear axis. With head_adaptive_ovalness on (default), the front-to-back and height scales shift by up to head_ovalness_strength (0.08) depending on ear flare, limited by head_min_width_scale (1.48) and head_max_height_scale (1.53). Both desktop apps show these under Head > Head Shape. Changing them makes preprocessing outdated.

Pinna2HRTF project head-preview accepts {"left": "...", "right": "...", "preprocessing": {...}, "folder": "..."} on stdin. It places the ears at the configured ear distance, builds the dummy head with the given head-shape settings at preview resolution, and writes head.stl, left.stl and right.stl to the folder. The reply lists the written paths. Both desktop apps show this preview under Head Shape, where it can only be rotated. Project Defaults in App Settings also has a Head Shape group, so new projects can start from your own head-shape values.

Legacy settings

Older settings files store the ear distance as preprocessing.head_radius. Loading and dry runs read it as ear_distance with a warning and leave the file unchanged. To update the file, save the project in the app or run:

uv run Pinna2HRTF migrate-settings pinna2hrtf.yaml

The command adds ear_distance, marks head_radius as deprecated, keeps comments, and stores the original as pinna2hrtf.yaml.head-radius-compat.bak.

Postprocessing defaults

By default, YAML postprocessing normalizes output with a −30 dB level offset and overwrites its output folder. Set postprocessing.normalize: false to skip normalization, postprocessing.overwrite: false to preserve an existing output folder, or postprocessing.resample_hrirs: true to resample HRIR files. Resampling defaults to 48,000 Hz. It changes HRIRs only; HRTF files are not resampled. Direct SOFA commands without a YAML config do not apply the level offset.

Standalone SOFA export stages the results and fails if an export filename already exists. For a binaural export, both simulations must use the same source positions in the same order.

For YAML runs, changes to the selected ears or recorded solver inputs require a fresh preprocessing run before NumCalc or SOFA export. A manual PPM fit must have a recorded source mesh and identity that match the selected ear.

Slurm

Set numcalc.mode: slurm and configure the cluster partition, QoS, memory, time limit, and array concurrency in the YAML file. The Slurm worker verifies completion of each frequency step, skips complete steps, and reruns incomplete steps when resubmitted. Preserve the project folder and its generated-output records when resuming.

Each submission writes its own read-only worker script to .pinna2hrtf/slurm and records the job ID of each ear in .pinna2hrtf/slurm-jobs.json. While a recorded job is pending or running, numcalc submits only ears without an active job and fails when both are active. Local NumCalc, other stages and resets fail until the jobs finish. Postprocessing in the same run is skipped; run it after the jobs finish. If the second ear cannot be submitted, the first stays queued and recorded, and the command fails; run it again to submit the missing ear. When squeue and sacct cannot report a recorded job, the command fails rather than submit again. To cancel the recorded jobs:

uv run Pinna2HRTF numcalc --config pinna2hrtf.yaml --cancel

Cancelled jobs are released once they leave the queue. Pinna2HRTF outputs status lists the jobs that have not finished.

To run a Slurm project once on the local machine without changing its YAML file, add --numcalc-mode local:

uv run Pinna2HRTF numcalc --config pinna2hrtf.yaml --numcalc-mode local

The desktop apps always run NumCalc locally this way and keep the saved mode.

Microphone positions

preprocessing.source_position_input_left and source_position_input_right set the microphone position in millimetres in the coordinates of the ear mesh used for preprocessing. When a position is confirmed through Pinna2HRTF project save, as the desktop apps do, the SHA-256 of that mesh is recorded in .pinna2hrtf/microphone-placements.json in the output folder. Saves that leave the position out keep the existing record, and saving the same coordinates again records the mesh as it is now. Preprocessing ignores a recorded position whose mesh has changed, logs it, and estimates the position instead. The position stays in the YAML file. Positions without a record, such as hand-written ones, are used as written.

Scan preparation from YAML

Enable scan_preparation, choose a scan and explicit crop rotation, and select the ears. The scan guide explains alignment, orientation checks, manual review, and provenance.

scan_preparation:
  enabled: true
  scan_path: /path/to/edited-head.stl
  rotation_degrees: 0
  prepare_left: true
  prepare_right: true
  target_edge_mm: 0.75
  require_manual_review: false
  reviewed_left: null
  reviewed_right: null

Run individual stages without YAML

Scan preparation and postprocessing need a YAML configuration. The other stages also accept standalone command-line options; --help lists them. For example:

uv run Pinna2HRTF scan-preparation --help
uv run Pinna2HRTF preprocessing --help
uv run Pinna2HRTF numcalc --help

Keep a separate output folder for each experiment and inspect the geometry and source placement after preprocessing before starting a long simulation.

Standalone preprocessing with --export-path keeps one previous export per ear: a replaced project moves to <name>-Left.previous (or -Right). An older backup is deleted only after you confirm, and only when it holds unchanged generated files and solver output. Backups with your own or changed files are kept as .previous-<date>. Pass --replace-previous-backup to confirm in scripts.

Project defaults

Pinna2HRTF project new-defaults accepts JSON on stdin with parent, index, and a defaults object containing integer minimum_frequency, maximum_frequency, frequency_steps, max_instances, max_cpu_load, and optional evaluation_grid. It returns a unique save_location, a complete default config for the new project, and validated preprocessing and numcalc defaults without creating a project folder.

Pinna2HRTF project save-defaults accepts {"path": "...", "defaults": {...}} and writes a Project Defaults file ("format": "Pinna2HRTF.ProjectDefaults", version 2). defaults holds project_directory, input_handling (copy or reference), evaluation_grid, the whole-number minimum_frequency, maximum_frequency, frequency_steps, max_instances and max_cpu_load, and a workflow object with the same keys as new-defaults. Values are checked with the project rules before writing. Pinna2HRTF project read-defaults accepts {"path": "..."}, checks the file the same way and returns {"defaults": ...}; it also reads version 1 files saved by earlier Windows builds.

Pinna2HRTF project defaults returns {"config": ...} with the default value of every editable project setting, grouped by settings section.

Pinna2HRTF project rules returns the validation rules both desktop apps apply. Each entry in fields names a setting id (the identifier used by the setting help), its config key, its kind (integer, decimal, or text), optional minimum, exclusive_minimum, maximum, multiple_of, optional, and when (the switch that must be on for the rule to apply), the message shown when the value is out of range, and the pipeline stages it blocks. relations lists cross-field checks: greater and at_least compare id with other, and any requires one of fields to be on. parse_messages holds the message for values that are not numbers.

Pinna2HRTF project check accepts {"config": ..., "stage": "preprocessing"} and returns {"issues": [{"id": ..., "message": ...}]}. Omit stage to check every stage. project save with a stage applies the same check and fails with the first issue.

Pinna2HRTF project validate-grid accepts {"path":"..."} and returns the resolved folder when it contains Nodes.txt and Elements.txt. Both commands return JSON errors and a nonzero exit status on failure.
