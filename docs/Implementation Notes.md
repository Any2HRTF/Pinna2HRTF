# Implementation Notes

Developer notes on conventions, file formats, compatibility rules and platform workarounds that the code relies on but does not explain. Each note names the code that owns the behaviour. User-facing CLI usage is in the [README](../README.md) and the [online documentation](https://any2hrtf.github.io/Pinna2HRTF/docs/).

## Scientific and numerical conventions

- **Quaternions from rotation matrices** (`HRTFCalculation/Inference/src/math_helpers.py` `get_quaternion_from_rotation_matrix`, mirrored in `numpy_math_helpers.py`). Shepperd's method: the numerically largest of `w, x, y, z` is the pivot, so no division by a value near zero happens. The trace-based formula fails for rotations near 180 degrees. Each candidate row is `(w, x, y, z)` scaled by 4 × pivot. The result is sign-normalised to `w >= 0`, because `q` and `-q` describe the same rotation. The NumPy and PyTorch versions must stay identical.
- **Elliptical ear cut** (`HRTFCalculation/Preprocessing/src/cut_eararea.py` `_ellipse_cut`). The cylinder runs along y and the ellipse lies in the xz plane. The x semi-axis applies `ear_cut_clearance_scale` twice and the z semi-axis applies it once. This asymmetry is the original behaviour, and existing meshes and HRTFs depend on it. Do not change it.
- **Ear canal cap** (`HRTFCalculation/Preprocessing/src/ear_canal_closer.py`). The cap is pushed slightly inward, toward the head, not outward.
- **Manual PPM shape-key bounds** (`HRTFCalculation/ManualPPMFitting.py` `_SHAPE_KEY_RANGES`). The weight bounds come from Perfler et al. (2025), Table 1. Only the two Crus helicis dent keys (`Upper dent`, `Lower dent`) are limited to `[0, 1]`. All other keys use `[-1, 1]`.
- **Manual PPM rotations** (`ManualPPMFitting._apply_controls`). Rotations are edited as ZYX Euler angles in degrees. The quaternion is recomposed with Blender's own `Euler(..., "ZYX")`, so editing one component leaves the untouched axes stable.
- **PPM network head** (`HRTFCalculation/Inference/inference_stl.py` `main`). The shipped checkpoints were trained with 188 outputs. If `PPM Parameters.csv` yields another count, it no longer matches the network head, and inference fails on an assertion.
- **Core ML inference precision** (`Scripts/coreml/PPMPredict.swift`). The helper pins `computeUnits = .cpuOnly` to keep float32 CPU behaviour the same on every machine. Running on the GPU or Neural Engine would be a numerical change and is never chosen implicitly. Core ML runs in a separate helper so that Blender's Python runtime stays independent of Core ML's native dependencies. Models are compiled during release packaging.
- **Core ML conversion checks** (`Scripts/convert_coreml_models.py`). These are build integrity checks only. They do not replace validating the full acoustics on representative ear scans. The compiled network fixes the architecture keys (`window_size`, `depths`, `num_heads`), and the runtime rejects a configuration that disagrees (`HRTFCalculation/Inference/model_runtime.py` `ARCHITECTURE_KEYS`).

### LocaDyn spatial upsampling

Owner: `HRTFCalculation/Postprocessing/locadyn.py`, called from `spatial_upsampling.py`. The README's "Numerical conventions" section has the summary. Details:

- **Tolerances.** The legacy MATLAB `optimset` `TolFun` sets both the function tolerance and the optimality tolerance. `_curvefit` therefore passes the same value as `ftol` and `gtol`. The reference off-axis fit uses `TolFun = 1` (`fit_toa`, `ftol=1`).
- **Fixed parameters.** MATLAB accepts equal lower and upper bounds for a fixed parameter. SciPy's `least_squares` needs strict bounds. `_curvefit` removes parameters whose offset is zero from the optimisation without changing the model.
- **Outlier threshold (a deliberate scientific choice).** `fit_toa` calls `outlier_mask(..., alpha=len(ir))`, so alpha equals the number of directions M. This matches the original LocaDyn call to `ziegelwanger2014` with `outlierDetection=1`, which passes `alpha = 1*M` to `deleteoutliers`. AMT's default is `prod([0.05;0.01])*M`. With `alpha/(2n) >= 0.5` the Grubbs critical value is about 0, so roughly half of the directions are excluded from the TOA fits even for Gaussian residuals. Do not change this without re-validating against MATLAB.
- **Sphere projection** (`subdivide`). Subdivided points go back onto the sphere through a MATLAB-style `cart2sph`/`sph2cart` round trip, not through division by the norm. Midpoints keep TriQuad's stable order and its four interleaved children per face.
- **Boundary faces** (`boundary_faces`). Faces are oriented like MATLAB `freeBoundary`: outward orientation, lowest index first, rows in lexical order.
- **Level** (`interpolate`, `upsample_file`). With `spatial_normalize: false` the dense set keeps the level of the HRIR export (`normalize` / `level_offset_db`). With `spatial_normalize: true` LocaDyn's frontal normalisation is applied on purpose: frontal RMS 0.01, which needs exactly one direction at (0°, 0°).
- **Delay** (`upsample_file`). The interpolated IRs already contain the modelled TOA. SOFA `Data.Delay` is an extra delay in samples, so it is written as zero. The TOA in seconds is kept in `upsampling_report.mat` as `toa_seconds`.
- **Metadata.** Descriptive `GLOBAL_` attributes are copied from the source SOFA. Convention-specific fields keep the `SimpleFreeFieldHRIR` defaults.

## Coordinate conventions and geometry

- **Camera positions** (`inference_stl.get_camera_position`). Spherical `(radius, azimuth φ, elevation θ)` becomes Cartesian as `x = r cos θ cos φ`, `y = r cos θ sin φ`, `z = r sin θ`.
- **Scan cropping** (`HRTFCalculation/Config.py` `ScanPreparationConfig`). `crop_polygon_xz` needs at least three vertices and must be strictly convex and consistently ordered. The archived half-plane crop works only on a strictly convex polygon. On Windows the default polygon exists only in YAML and is preserved when a project is imported (`MainWindow.xaml.cs`, `crop_polygon_xz` handling).
- **Scan preparation geometry** (`HRTFCalculation/ScanPreparation.py`). The attachment boundary keeps whole Poisson triangles (`restore_attachment_boundary`). Cutting triangles one at a time duplicates the intersection vertices and leaves hairline cracks. MeshLab deliberately skips some degenerate three- and four-edge loops. Trimesh's narrow `fill_holes` handles only those remaining micro-holes (`close_non_attachment_boundaries`).
- **Dummy head** (`HRTFCalculation/Preprocessing/__init__.py` `run_preprocessing_pipeline`). `dummy_head.stl` is shared by both sides and lives at the work root. A right-only project therefore never gets an artificial `Left` folder.
- **Mesh2HRTF evaluation grid label** (`HRTFCalculation/Preprocessing/src/solver_paths.py`). Mesh2HRTF uses the grid label to find and name the output grid. Renaming a grid changes the paths written into the project.
- **Mesh editor plane** (`Sources/Pinna2HRTF/Services/MeshEditorModel.swift` `planeOrigin`, `Models/MeshEditorModels.swift`). Flip changes which side is kept, not where the cutting plane sits. The drawn rectangle is a compact display of the mesh/plane intersection. Its size changes only the overlay, because the backend always cuts a half-space. A plane outside the mesh stays visible by using the mesh's projected footprint.
- **Lasso selection** (`MeshEditorModel.selectPolygon`). Only faces whose projected centroids lie inside the lasso are candidates. The default front-surface mode also checks the closest hit for occlusion.
- **Orientation axes** (`Sources/Pinna2HRTF/Views/CoordinateSystem.swift`). The axes are display-only. They are excluded from mesh hit testing and from saved output. Axis length extends well past the scan, and the thickness follows the mesh size, not the axis length. The camera-linked orientation reference stays visible even when the scan's origin is outside the viewport.

## Project, settings and receipt formats

- **One-ear projects** (`Config.py` `PathsConfig`). There are no implicit demo ears. A one-ear project saved with `exclude_none` must reload as a one-ear project.
- **Deprecated postprocessing keys** (`Config.py` `PostprocessingConfig`). `matlab_executable` and `amt_path` are ignored, because spatial upsampling now runs in Python. They are still accepted because older configs contain them and the models use `extra="forbid"`. The Mac config writer no longer emits them (`Services/PipelineConfigWriter.swift`), and `StageReceipt.signature` drops them from postprocessing signatures.
- **Settings from the desktop apps** (`Services/PipelineConfigWriter.swift`). Settings the app does not expose use the pipeline defaults. Imported overrides are merged separately from the preserved configuration.
- **Preserved configuration** (`ProjectDocument.cs`, `ProjectRecord.preservedConfigJSON`). A validated document that was read from disk is the base for every app save. Only fields owned by desktop controls are replaced, so YAML-only settings survive app saves. Imported alignment provenance keeps the read-only source, so Reset Outputs can recover it.
- **Aligned scan provenance** (`MeshEdits/AlignedScan.json`, `source_path`). The aligned scan can never be its own source. Re-opening alignment recovers the original scan from this report (`Stores/AppStore.swift` `beginScanAlignment`). On Windows, editing an outdated reviewed mesh reopens its original source (`WindowsWorkflow.cs`).
- **Settings revisions and merged saves** (`HRTFCalculation/Project.py` `merge_settings`, `settings_lock`). A settings revision is the SHA-256 of the file bytes. `project save` compares the expected revision under `.pinna2hrtf/settings.lock` next to the settings file, a lock separate from `outputs.lock` because the Windows app already holds the output lock when it saves settings for a run. A conflict raises `SettingsRevisionConflict` before anything is written. In a merged save only `EDITABLE_SETTINGS` keys come from the client. An omitted key keeps the saved file's value (or the preserved snapshot's when no file exists yet), so a client clears a key only by sending `null`. Sending `ear_distance` drops a legacy `head_radius`. `numcalc.mode` is not editable: the apps pass `--numcalc-mode local` for each NumCalc run (`CLI.py` `run_config`) and never change the saved mode. The Mac app records an explicit switch to the automatic microphone position in `ProjectRecord.automaticMicrophoneSides` and sends `null` for it. Positions it cannot verify are omitted. The Mac and Windows registries store the last loaded or saved revision (`settingsRevision`, `SettingsRevision`). Duplication drops it, so the copy's first save is unchecked.
- **Microphone placements** (`HRTFCalculation/MicrophonePlacement.py`, `<output_dir>/.pinna2hrtf/microphone-placements.json`). Format `pinna2hrtf-microphone-placements-v1` stores `position_mm` and `mesh_sha256` per side. `PreprocessingConfig` forbids extra keys, so the identity lives beside the YAML file and applies only while `position_mm` equals the YAML coordinate. A merged save stamps a position the client sent with the SHA-256 of the mesh that `RunConfig.preprocessing_input_paths` selects, keeps an existing stamp for an unchanged position, and records a saved position the client omitted with `mesh_sha256: null`, because the client could not confirm it. A run ignores a stamped position whose mesh hash differs and any position recorded with a null hash. It logs a message and estimates the position. The YAML coordinate is kept. `CLI.py` removes such positions before the run, so the preprocessing receipt matches the effective settings. `run_preprocessing_pipeline` checks again because an earlier stage in the same run may have replaced the mesh. Positions without a matching record, from hand-written or legacy settings, are used as written, as before.
- **Mesh identity strings** (`ArtifactScanner.meshIdentity`, `meshIdentityMatches`). Identity records are `path|size|modified`, with the size and time after the last pipes. Timestamps can round slightly when a project is copied between volumes or serialised through JSON. Matching therefore accepts sub-microsecond differences (`< 1e-6` s) and does not treat them as changed geometry.
- **Copy-input projects** (`ArtifactScanner`; `StageReceipt.mac_capture`). A copy-input project records the portable in-project copy as its input. The source fingerprint still lets changes to the selected original invalidate the prepared geometry. When a project is loaded, a copied input inside the project wins over a missing original path (`Services/ProjectConfigDocument.swift` `restore`).
- **Core ML checkpoint identity** (`HRTFCalculation/StageReceipt.py` `signature`, `mac_checkpoint_fingerprint`, `mac_source_checkpoint_path`). A `.coreml.json` manifest records toolchain versions and changes with every rebuild. A model's identity is therefore the `source_checkpoint_sha256` of the PyTorch checkpoint it was converted from, which also keeps PyTorch-era receipts valid. `X.coreml.json` stands for `X.pth`. On Windows, a Mac project's `.coreml` checkpoint names resolve back to the PyTorch checkpoint (`MainWindow.xaml.cs`).
- **Checkpoint resolution on macOS** (`HRTFCalculation/Inference/model_runtime.py` `checkpoint_path`). The Mac release ships no `.pth`, so a missing checkpoint resolves to its conversion. A checkpoint that is present wins, unless the conversion was made from exactly that file (matching SHA-256). A retrained model must never run stale weights. Windows, source and CLI environments keep the PyTorch path. On those platforms PyTorch is imported only when it is used, so Mac Core ML inference never imports it (`get_model_prediction`).
- **Inference inputs** (`inference_stl.main`). Scan preparation writes each ear as both `.stl` and `.ply`. Inference processes each stem once and prefers `.stl`.

### Stage receipts and legacy formats

Owner: `HRTFCalculation/StageReceipt.py`. Both apps ask `project stage-status` for a final verdict and keep no receipt logic of their own (`Services/StageReceipt.swift`, `WindowsStageFreshness.cs`).

Preprocessing verification uses `HRTFCalculation/SolverProjectFiles.py` to fingerprint the solver decks, object meshes, evaluation grids and project parameters. Solver results are outside this fingerprint. The Mac sidebar reuses receipt verdicts in the initial and detailed passes of one refresh. A new refresh reads new verdicts.

- Current receipts: `.pinna2hrtf-{inference,postprocessing}-receipt.json` with `version: 2` (`signature`) and `.pinna2hrtf-preprocessing-inputs-v1.json` (`RunConfig.preprocessing_input_signature`). They need only the pipeline `config`.
- Older receipts hash the app's own project record, so the request must carry `app` and that app's saved `project`. Without it the verdict is `legacy-unsupported`. A shared receipt always wins over an older one.
- Postprocessing is current only when its receipt matches and, with spatial upsampling enabled, every `Upsampled/HRIR_*/upsampling.json` records `LocaDyn-1948`, the current subdivisions and normalisation, the input and dense output identities (`size`, `mtime` within 1 ms) and the dense file is an HDF5 or netCDF container (`spatial_upsampling_current`).

#### Mac formats

- Inference and postprocessing: the receipt file holds a lowercase SHA-256 hex digest of `JSONSerialization` output with `.sortedKeys` (`mac_stage_signature`). Inference hashes the base64 of the pretty-printed sorted `InferenceSettings` (checkpoint mapped to `.pth`), the pipeline ear, preprocessing mesh, model and checkpoint fingerprints. Postprocessing hashes the base64 of the pretty-printed `PostprocessingSettings`, the preprocessing signature string and the SOFA fingerprints of the export folder and of each selected ear's `Output2HRTF`.
- Fingerprints are `sha256:<hex>` of the symlink-resolved file, `unavailable` for a missing or non-regular file and an empty string for an empty path.
- Byte format (`darwin_json`, `darwin_pretty`): keys are ordered as Foundation's case-insensitive numeric collation orders them (punctuation, then digits by value, then letters, with accents and then lowercase breaking ties). Doubles use `%.17g`, `/` is escaped as `\/`, control characters use short escapes or lowercase `\u00xx`, and other characters are written raw. Pretty printing indents two spaces and writes `"key" : value`.
- Preprocessing: `.pinna2hrtf-preprocessing-mac-v2.json` wins over `.pinna2hrtf-preprocessing-signature` (`mac_preprocessing_matches`). Numeric strings in the compared configuration become doubles as Swift's `Double(String)` parses them.
- A receipt written for both ears also covers a later selection of either ear.
- Line-based receipts: early receipts have seven newline-separated fields. Later receipts add three manual-fit fields (index 7 holds the manual PPM settings, 8 and 9 the left/right fitted mesh stamps). A receipt may also have an eleventh scan-preparation settings field. Seven-field receipts are padded with empty manual-fit fields before comparison. Settings fields decode as Swift's synthesized `Decodable` does: required keys must be present, unknown keys are dropped (`swift_decode`).
- A legacy receipt is never accepted blindly, and genuinely changed settings are never re-baselined. The effective configuration must match exactly.
- The compared configuration covers the inputs and effective settings that determine preprocessing results. Imported physical and geometry overrides from the preserved configuration are included, because they also affect results. Keys that the GUI settings already represent are removed from the imported part. Storage locations, the input-copy policy, inactive settings and bookkeeping or export-only choices do not affect the solver and are excluded.
- A legacy receipt has no resource hashes. A consistent move of the project root (the same trailing path components under a new prefix) is accepted for model and grid resources only after both ear stamps were verified.
- Ear reviews count when their receipt's `source_identity` and `output_identity` match within 1 ms (`mac_review_is_current`). A manual fit counts when its source identity matches within 1 µs (`mac_mesh_identity_matches`).

#### Windows formats

- Stamps are uppercase SHA-256 hex digests of `System.Text.Json` output with default options (`dotnet_json`): properties in declaration order as the app sends its record, `"` as `\u0022`, HTML-sensitive characters, DEL and all non-ASCII characters as uppercase `\uXXXX` (UTF-16 surrogate pairs above U+FFFF), and shortest round-trip numbers with `E` exponents below 1e-4 and from 1e15.
- Mesh identities are `fullpath-lowercase:size:ticks:sha256`, with ticks as .NET UTC ticks (`windows_mesh_identity`).
- Inference: `.pinna2hrtf-inference-signature` hashes `{"Inference": …, "inputs": [left ear, right ear, model, checkpoint identities]}`.
- Preprocessing: `.pinna2hrtf-preprocessing-windows-v3.json` holds, per selected ear, the app's `preprocessing` config section without `enabled`, `title`, `pictures`, `write_intermediates` and the other ear's microphone, plus mesh and grid SHA-256 values. It is compared as JSON with numbers compared as doubles. Older projects have `.pinna2hrtf-preprocessing-signature` with a stamp of the preprocessing, inference, manual PPM and scan preparation settings and both preprocessing mesh identities.
- Postprocessing: a non-JSON `.pinna2hrtf-postprocessing-receipt.json` hashes the stamp of the postprocessing settings and the v3 preprocessing document, followed by `path:sha256` lines for every export, upsampled output and `Output2HRTF` SOFA file, sorted case-insensitively.

## Output ownership

Owners: `HRTFCalculation/Outputs.py` (manifest store, `classify`, `reconcile`, `begin`, `reset`), `HRTFCalculation/RunConfig.py` (`_read_output_manifest`, `_record_published_outputs`, `_publish_export`). The desktop apps call these through the `outputs` and `output-worker` commands.

- **Manifest** (`.pinna2hrtf/generated-output-manifest.json`, `Version: 1`). It stores `Files` (relative path → `Stage`, `Size`, `ModifiedUtcTicks`, `Sha256`), `Directories` (relative path → stage) and an optional `Pending` run. No absolute paths or GUI project IDs are stored. The manifest is optional project metadata, and a missing one means nothing is owned yet.
- **Shared timestamps.** `ModifiedUtcTicks` uses .NET ticks (`st_mtime_ns // 100 + 621355968000000000`). Published SOFA files get whole-second mtimes, so Python, Swift and C# compute identical ticks (`_record_published_outputs`).
- **Case-insensitive keys.** Manifest paths are matched case-insensitively (`_manifest_key`), because the Windows app compares them that way.
- **Exact producer conventions.** Only paths that match the documented producer patterns in `Outputs.FILES` and `Outputs.DIRECTORIES` are claimed. Generic `*.json` / `*.txt` or recursive folder ownership is never claimed. The NumCalc patterns also recognise partial NumCalc runs that were copied in from outside.
- **Claiming new files** (`begin`, `reconcile`). Before a stage runs, the existing files are snapshotted into `Pending`. Only files that appear or change during the run, and that match a producer pattern, are claimed. A directory difference alone does not prove that our process produced an unrelated file. Pre-existing unowned files are never claimed, and an earlier manual edit is never blessed. Scan preparation, inference and postprocessing claim only files classified to their own stage.
- **Pre-manifest projects.** An existing directory that matches a producer pattern and is empty is adopted. Removing an empty known directory cannot remove user data, and it lets later resets clean up the shells of failed stages.
- **Input overlap check** (`begin`). A stage refuses to start when a protected input is a file or folder that the stage itself produces. Files in the editor folders (`MeshEdits`, `Manual PPM`) are skipped by this check: only the ear editors publish there (`EditorPublication.py`), no pipeline stage writes them, so a project's own manual fit or aligned scan can be an input to preprocessing or scan preparation.
- **Protected inputs across projects** (`RunConfig.run_postprocessing`). A SOFA output folder may lie outside the project. The desktop apps pass every listed project's inputs in `PINNA2HRTF_PROTECTED_INPUTS` (a JSON list of paths), and the export refuses a destination that contains or lies inside any of them.
- **File permissions** (`Outputs.replace_text`). Settings, manifests, receipts and ledgers are replaced atomically through a temporary file created with the process umask. An existing target keeps its mode.
- **Reset** (`reset`). Only unchanged owned files are deleted (SHA-256 and mtime are checked again just before unlinking). Edited files are kept on purpose and counted as `modified`, and only errors block completion. Directories are removed only when they are empty (`rmdir`, which cannot delete files added concurrently). Paths whose resolved form differs from their spelling (links below the project root) are skipped. Link components at or above the root, such as `/tmp`, `/var/folders` or a linked Dropbox folder, are the user's choice. Editor folders (`MeshEdits`, `Manual PPM`) and protected inputs are never reset. Archived fitting templates are copied once and then reused as sources, so a later fit save must not claim external changes to that copy.
- **Saved fits on reset** (`Models/PipelineModels.swift` `protectedOutputInputs`). A project's saved fits count as outputs when that same project is explicitly reset. Fits used by any other project stay protected inputs. Resetting generated fits keeps the selected ear-model method and prompts for missing fits.
- **External SOFA destinations** (`.pinna2hrtf/external-sofa-outputs.json`, `Outputs.reset`, `RunConfig._publish_export`). Destinations outside the project have their own explicit ownership ledger (absolute path → SHA-256). No directory there is deleted recursively, and pre-existing files there are never claimed. A copied project never inherits ownership of the original's external results (`Project._duplicate_locked` deletes the ledger in the copy). Internal SOFA files remain tracked by the main manifest. The standalone SOFA export (`RunConfig.sofa_cli`) never deletes anything in a user-selected directory.
- **Export publication** (`RunConfig._publish_export`, `run_postprocessing`). The manifest is read once, and only files whose current hash matches a manifest entry may be replaced. If a rollback fails, the recovery copies stay in the staging folder and the log names their location.
- **Spatial upsampling staging** (`spatial_upsampling.upsample_hrtf_files`). The pipeline always passes a fresh export folder. Overwrite handling happens when that folder is published by `RunConfig._publish_export`. Dense exports are published together, and only after interpolation and SOFA validation succeed.

- **Hash cache** (`FileIdentity.cached_sha256`). Receipt and freshness checks reuse SHA-256 digests across processes. The cache lives in the user cache folder (`~/Library/Caches/Pinna2HRTF`, `%LOCALAPPDATA%\Pinna2HRTF`, or `$XDG_CACHE_HOME/Pinna2HRTF`), holds up to 4096 entries, and keys each entry by resolved path, inode, size, mtime and ctime. A rewrite therefore invalidates the entry even when the mtime is restored. A digest is cached only when the file did not change while it was being hashed.

## Preprocessing exports and backups

Owner: `HRTFCalculation/Preprocessing/__init__.py`.

- **Recognised solver outputs** (`_NUMCALC_OUTPUT` and the related patterns). These are the exact names of files that NumCalc, Pinna2HRTF's NumCalc runner and Mesh2HRTF's Output2HRTF add to a project after export (see `NC_Main.cpp`, `NumCalc.py`, `output2hrtf.py`, `write_output_report.py`, `inspect_sofa_files.py`, `export_vtk.py`). Any other unrecorded file means a backup is kept.
- **One previous export per ear** (`plan_export_backups`, `previous_backup_path`). A replaced project becomes `<project>.previous`. The desktop/config route cannot prompt, so an older backup may be deleted only if it holds unchanged generated files. Otherwise it is kept as `<project>.previous-<YYYYmmdd-HHMMSS>`. Approved backups are fingerprinted again just before deletion, and only the exact folder that was confirmed is deleted. The standalone CLI asks for `--replace-previous-backup` instead.
- **Fail before work.** Input meshes are loaded and validated before any previous output is cleaned. In the standalone export route (`export_path`), an existing target that is not a generated Pinna2HRTF project, or that contains input files, stops the run before any work starts.
- **Intermediates.** Legacy and previous intermediate files are preserved, because these folders can hold inputs, inference results and files changed outside the app. A generated intermediate keeps one `<name>.previous` copy. The older copy is replaced only if it still matches the fingerprint recorded when it was made (`_read_previous_record`). Edited, unrecorded or unusual copies are kept with a date. A `.previous` that is, or holds, a selected input is never moved or replaced. An unused side directory is removed only when no inference results or unfamiliar files remain.
- **Publication.** Both the app/config and the standalone export publish only after every side has been generated in a staging folder. Existing projects are kept, including unknown or externally modified files.
- **Prepared meshes** (`ScanPreparation.prepare_scan`). An input is never overwritten, even if a project points at generated output: the source scan must lie outside `Prepared`. No prepared mesh is published until all selected ears pass validation. `_validated_prepared_ears` caches prepared-ear digests whose serialised topology already passed in this process.

## NumCalc

Owners: `HRTFCalculation/NumCalc.py`, `HRTFCalculation/RunConfig.py` (`slurm_worker_text`), `Sources/Pinna2HRTF/Services/ArtifactScanner.swift` (`directCompletedSteps`, `frequencyStepComplete`), and the matching code in `Sources/Pinna2HRTF.Windows/MainWindow.xaml.cs`.

- **Step completion.** A step counts as complete when `be.out/be.<step>/{pBoundary,pEvalGrid,vBoundary,vEvalGrid}` all exist and are non-empty, and either its `NC<step>-<step>_log.txt` contains `---------- NumCalc ended:`, or the shared `NC.out` of a direct, all-frequency run reports the step as solved.
- **Why `NC.out` is checked per step.** `-estimate_ram` writes the same `NC.out` with every step header but solves nothing. Only a solved step reports its own `Time Statistic For The Current Step`. An `NC.out` with step headers alone is therefore not a completed run. The file must also contain an `End time:` line.
- **SLURM worker** (`slurm_worker_text`). The per-step check in the generated bash script tests only the four outputs and the step log. Steps solved by a direct run (`NC.out` only) are not recognised there and are computed again.
- **Slurm submission** (`RunConfig.run_numcalc_slurm`, `release_finished_slurm_jobs`, `cancel_numcalc_slurm`). Each ear is one array job submitted with `sbatch --parsable` and a fresh read-only worker script `.pinna2hrtf/slurm/numcalc-<side>-<YYYYmmdd-HHMMSS>-<hex8>.sh`. Slurm copies the script at submission, and no later submission rewrites an earlier worker. The legacy shared `run_numcalc_array.sh` is no longer written or removed. After each accepted submission, `.pinna2hrtf/slurm-jobs.json` is replaced atomically: `{"Version": 1, "Jobs": [{"Side", "JobId", "Cluster", "Project", "Steps", "SubmittedUtc", "Worker", "WorkerSha256", "Cancelled"?}]}`. `Cluster` is the optional cluster from the `sbatch` reply and is passed as `--clusters` to later queries. If the record cannot be written, the job just accepted is cancelled. A failed second submission leaves the first job queued and recorded, so a retry submits only the ear without an active job.
- **Slurm job state** (`slurm_job_state`). `squeue --jobs <id>` listing the job means active, an empty reply or `Invalid job id` means finished. Otherwise `sacct --allocations` decides from the job state. A job that neither command can report is `unknown` and treated as active, except after a successful `scancel`. Finished jobs are dropped from the record whenever outputs are reconciled, and their worker script is deleted only if it still matches `WorkerSha256`.
- **Slurm output ownership** (`Outputs.reconcile`, `Outputs.begin`). The NumCalc reservation (`Pending` in the generated-output manifest) stays open while recorded jobs are active or unknown. Each reconciliation claims solver files produced since the reservation began, skips files that change while they are hashed, and closes the reservation once every job has finished. A NumCalc retry reuses the open reservation. Other stages, local NumCalc and resets that include NumCalc fail while jobs are active. `Pinna2HRTF numcalc --config <settings> --cancel` runs `scancel` for the recorded jobs and marks them `Cancelled`.
- **RAM estimate output** (`_estimate_ram`). NumCalc's console output for `-estimate_ram` goes to a temporary file outside the project tree. It is needed only to explain failures.
- **Scheduling** (`run_local_numcalc`). Projects passed explicitly by the app or config route are used as given, so sibling backups such as `Left.previous` are never scheduled. Before NumCalc runs, the existing file names are snapshotted (`ownership`). Only newly produced files can be claimed, and pre-existing unrecorded files stay protected. As in Mesh2HRTF's `manage_numcalc`, `wait_time` lets a newly started instance ramp up before CPU load decides whether to start another. Completion is polled every second, and `wait_time` only throttles new starts.
- **Pressure files** (`HRTFCalculation/PressureField.py` `_pressure`, `_frequencies`). NumCalc's pressure file holds a version line, the number of groups, then for each group a `group ID / count` line followed by `ID real imaginary` rows. Frequencies come from the solver's `Load Frequency Curve` in `NC.inp`, not from a reconstructed linspace.

## Legacy compatibility

Code marked "version compatibility only" is planned for removal in a future release.

- **Legacy `head_radius`** (`HRTFCalculation/Compatibility.py` `import_legacy_distance`, `annotate_legacy_distance`; `Config.PreprocessingConfig.legacy_distance`; CLI `--head-radius`). It maps to `ear_distance` (millimetres). Loading (`Config.load_config`) converts in memory only and warns while the file has `head_radius` without `ear_distance`; `project load`, `project read` and dry runs never write the settings file. The file is annotated in place only by the explicit `Pinna2HRTF migrate-settings` command (`Compatibility.main`), after the whole file passes validation. A flow-style `preprocessing` mapping is expanded to block style, because an inline YAML comment would swallow its closing brace and the members after it. The rewrite never replaces a file that changed during loading, never writes YAML that parses to different settings, keeps a `.head-radius-compat.bak` copy, and leaves read-only files untouched even where the directory would allow the replacement.
- **Settings encodings** (`Compatibility.read_settings`). Files with a UTF-8 or UTF-16 BOM use that encoding. Otherwise UTF-8 is tried, then cp1252, then latin-1. Older Windows builds wrote ANSI (cp1252) settings. cp1252 leaves five byte values undefined, and latin-1 decodes every byte, so loading cannot fail at this step. The detected encoding is reused when the file is rewritten.
- **Project registry geometry** (`Services/HeadGeometrySettings.swift` `migrateRegistry`, `Sources/Pinna2HRTF.Windows/HeadGeometry.cs` `MigrateRegistry`). An unreleased review build stored per-side targets (`earDistanceLeft` / `earDistanceRight`), which are averaged into `earDistance`. Otherwise a `headRadius` is used when `useCustomHeadRadius` was set or absent. The legacy keys are then removed. On Windows, registries without `numericFormat: invariant-1` have decimal-comma numbers normalised once. The Mac registry store keeps the exact original as `projects.json.pre-1.1.1-<uuid>.bak` before a geometry migration is persisted (`Stores/ProjectRegistryStore.swift` `load`).
- **Legacy mesh gamma** (`ProjectRegistryStore.migrateLegacyMeshSettings`). `meshGammaLeft` / `meshGammaRight` become `meshGamma` 0.2 and `meshGammaOpposite` 0.1.
- **Legacy folder names** (`Stores/ProjectLibrary.swift` `importedRecord`). The user's folder is never changed. On case-sensitive volumes a legacy lowercase `intermediates` folder is not found under its current name, so the import reports it and asks the user to rename it.
- **Legacy log location** (`Stores/ActivityLog.swift`). Logs that cannot be moved to the new log directory stay where they are, and lookup falls back to the legacy location. Errors during that move are ignored on purpose.

## Duplication and path relocation

Owner: `HRTFCalculation/Project.py` (`duplicate`, `relocate`, `publish_copy`, `execute` `load`). Both apps call `Pinna2HRTF project duplicate`.

- The copy is built in a private `.pinna-copy-<uuid>` staging folder next to the destination. Only a complete project is published, through an exclusive rename (`renamex_np(RENAME_EXCL)` on macOS, `renameat2(RENAME_NOREPLACE)` on Linux). An existing destination is never replaced. A failed copy never appears in the project list.
- Projects that contain symbolic links or reparse points are refused, so no content outside the selected project is copied. The source is snapshotted and hashed, and duplication aborts if it changed during the copy.
- Only app-produced metadata is rewritten: the settings files, the output manifest and JSON/YAML files that match an owned producer pattern. Geometry, logs and other user files are never edited, files with non-JSON content are copied unchanged, and a file is rewritten only when relocation changed it. Internal paths and source fingerprints move together, and external inputs stay referenced.
- Identity records append size and time after a pipe. Relocation matches the original root as a path prefix and does not split on colons, so Windows drive letters survive. Both the resolved and the spelled source root are tried.
- Rewritten owned files get new manifest fingerprints. An owned file whose original no longer matches its manifest hash is never blessed, and its entry is left as it was. Geometry timestamps and bytes are preserved by `copytree`/`copy2`. `Pending` is cleared.
- The preserved configuration JSON string is also relocated, so it does not point back to the original project.
- **Loading moved projects** (`execute` `load` with `folder`). Paths are rebased from the recorded `output_dir` to the actual folder. A POSIX absolute path becomes drive-relative when Windows reads it, and Windows resolution may prefix `C:` to `/Users/...`. The original root spelling is therefore read from the raw YAML, and a leading drive prefix is stripped before matching.

## Platform workarounds

### macOS

- **SMB status checks** (`ArtifactScanner.Inspection.attributes`). For regular files, status and validation use `URLResourceValues` with only size, modification date and resource type. FileManager's full attribute dictionary also fetches extended attributes, and on SMB volumes those extra requests block the status and validation views. Directories, symbolic links and special files still use `attributesOfItem`. One refresh owns one `Inspection`, and later refreshes always read fresh files.
- **Project directory migration** (`Stores/ProjectStatusController.swift`). Only app-managed local projects (under the app data `Projects` folder) are migrated during a refresh. Imported projects keep their folder layout, and listing a server root can stall.
- **SIGPIPE** (`App/Pinna2HRTFApp.swift` `init`). SIGPIPE is ignored for the whole app, so writing to a subprocess that already exited fails with `EPIPE` and does not kill the app. `CLIWorker` treats `EPIPE` as a dead worker.
- **Appearance** (`Pinna2HRTFApp.applyAppearance`). Appearance is applied through `NSApp.appearance` and on every window. `preferredColorScheme(nil)` does not fully revert a forced scheme (stale materials and layers remain), and it never reaches the AppKit editor windows.
- **Process trees** (`Services/ProcessTreeTerminator.swift`). NumCalc is started through `setsid`, so jobs can leave the parent's session. Stopping repeats until nothing tracked is left: SIGSTOP the tree top-down and re-snapshot until no new member appears, so nothing can fork or exit and reparent while it is examined. Then SIGTERM every member and SIGCONT so the signal can be handled, wait a grace period, and SIGKILL survivors. Orphans that kept the session or process group of a member seen earlier are included. Every signal goes only to a PID whose start time still matches the one recorded when it was first seen, which guards against PID reuse. Foundation reaps the root, which is killed directly if it is still running.
- **Pipe draining** (`Services/PipelineLogCapture.swift`, `ProcessLauncher.runHelper`/`drain`). A grandchild, such as a detached NumCalc, can inherit the output pipe and keep it open after the direct child exits. The final drain is therefore non-blocking and bounded (two seconds after exit). A lock guards reads against the final drain and the close that follows it.
- **JSON line workers** (`Services/CLIWorker.swift`, `fit-worker`/`mesh` sessions). Each request is one JSON object per line on stdin, answered by exactly one JSON object per line on stdout. Bytes after a newline are kept for the next reply. Lines that are not JSON objects (stray library output) are logged and skipped, so each request still pairs with one reply. After a timeout or failure the worker is killed and never reused, because a late reply would pair with the next request. A worker that died keeps no fitting state, and only a fresh `initialize` may start a new one (`Services/PPMFittingModel.swift` `execute`).
- **Warm Blender scene** (`ManualPPMFitting._export`). BezierPPM normally reopens its bundled `.blend` for every export. During interactive fitting the scene stays loaded and only the rig is updated. Per-vertex PPM-to-target distances are written next to the preview geometry, so the app can colour the surface without another distance pass.
- **SceneKit layout** (`Views/MeshSceneViewport.swift`, `MeshViewerView.swift`, `MeshWorkspaceSplitView.swift`, `NativeMeshWorkspace.swift`, `AppSettingsView.swift`). SceneKit's drawable size is kept out of SwiftUI split-view sizing, and minimum/ideal sizes never come from the last rendered frame. Split-divider drags do not always deliver AppKit's live-resize notifications. A hidden zero-width pane can leave `NSSplitView`'s old divider painted over the expanded Metal viewer, so the inspector is removed from the split entirely. Pane sizes are owned by the split view, because SwiftUI's inspector would otherwise keep changing `NSHostingView` minimum constraints during the window's constraint pass. The Settings window gets an explicit height from the measured pane, because letting the `TabView` size itself from the form's ideal height makes AppKit loop on constraint updates while the window resizes. Camera state is read and saved on the main thread, outside renderer and layout callbacks, and is not published, because publishing each redraw invalidates the viewer layout.
- **Trackpad navigation** (`Views/NavigableSCNView.swift`). Precise scroll events are two-finger trackpad gestures (orbit, or pan with Shift). They never enter the primary-button path used for face clicks and lassos. A conventional mouse wheel still zooms.
- **Fitting scene camera** (`Views/PPMFittingSceneView.swift`). SceneKit may use its own camera after navigation. Preview changes keep that camera and its pan target until an explicit view command.
- **Rig and target rendering** (`PPMFittingModel`, `Services/PPMTargetAppearance.swift`). The rig is drawn through the surface, like Blender's armature In Front option: curved cyan B-Bones and yellow controls without depth testing. The semi-transparent target uses a single-layer pass that needs depth writes to discard rear surfaces. `renderingOrder` draws it after the opaque, distance-coloured PPM.
- **Accessibility** (`Views/PPMFittingView.swift`, `EditorSheetLayout.swift`). Inspector sections use plain headings, not `GroupBox`, because `GroupBox` crashes the accessibility helper here. Controls stay ordinary labelled children, and the inspector's accessibility tree is not combined.
- **Lighting** (`Services/EvenMeshLighting.swift`). Symmetric world-space directional lights keep both ears equally lit. A soft angled key light follows the camera to show surface contours without darkening one side permanently.
- **Project removal** (`Stores/ProjectLibrary.swift` `removalPlan`, `isProtected`). A folder goes to the Trash only if the app created it or it carries the project marker, it is not a protected location (system folders, home folders, the app's own folders, volume roots such as `/Volumes/Data`), and it neither contains nor lies inside another listed project. Links are resolved first, and containment is component-aware (`/a/b` contains `/a/b/c`, not `/a/bc`).
- **Project list** (`Stores/ProjectRegistryStore.swift`). Writes are atomic and run on a private serial queue. The last readable version is copied to `projects.backup.json` before the primary file is replaced. The bytes last known to be on disk are kept in memory, so a save fully decodes the file on disk only when someone else changed it. An unreadable list blocks saving until the user restores or starts a new list, and the unreadable original is always preserved.

### Release packaging (macOS)

Owners: `Scripts/build_release_app.sh`, `Scripts/prepare_external_tools.sh`, `Scripts/trim_macos_runtime.py`, `Scripts/dmg/`.

- A release must contain the native solver, the mesh grader and the Blender exporter even in a fresh checkout or worktree. The build never silently packages an incomplete pipeline. External tools are always rebuilt, because an untracked binary from an older commit survives a checkout.
- `install_name_tool` invalidates the ad-hoc linker signature, and arm64 kills unsigned binaries. Every rewritten binary is therefore re-signed (`codesign --force --sign -`).
- SwiftUI compiler plugins are checked before packaging the runtime. The minimum macOS version (13.0) and the SDK are recorded with `vtool`.
- The layered icon is compiled when full Xcode (`actool`) is available. A previously compiled icon is reused only for exactly the same source, which also supports hosts where Apple's Icon Studio exporter cannot run. Command Line Tools builds use the bundled `.icns`.
- Core ML conversion uses build-only tools. The conversion packages and PyTorch are not kept in the app. The project and `uv.lock` stay compatible with Windows and CLI installs, and only the packaged Mac environment drops the PyTorch dependency closure (`trim_macos_runtime.py`). The model manifests authenticate the original source files and every compiled asset before the training checkpoints are omitted.
- `trim_macos_runtime.py` validates the whole removal set first, including files that other kept distributions also own, and never follows links out of staging. It removes only `site-packages/tests`, `torch/include` and the `tests` trees of an explicit package list, which hold unit tests and example meshes. It keeps `torch.testing`, `scipy._lib._testutils`, Blender scripts, native plugins, licences and dist-info metadata, because runtime imports can depend on them.
- Blender can start Python with its own cache settings. Its bundled startup and add-on scripts are precompiled, so the first launch cannot add files to the sealed resources.
- Wheels flatten Qt's versioned framework symlinks. The canonical framework layout is restored before signing, because duplicate `Resources/Info.plist` copies make `codesign` treat a framework as an ambiguous application bundle.
- **Settings panes** (`Views/AppSettingsView.swift`, `Sources/Pinna2HRTF.Windows/AppSettings.cs`). Project Defaults holds every value copied into a new project: files, simulation and calculation (parallel NumCalc instances, CPU load limit). Existing projects keep their own values, edited in the inspector.
- The Help menu opens the online documentation on both platforms. Windows also provides F1; its portable package does not include an offline website copy.
- The packaged Mac app uses macOS filesystem compression. The build verifies the signature again after compression. The app keeps all runtime files and models locally. Disk usage depends on the destination filesystem, and the logical file sizes are unchanged.
- DMG layout: the window geometry and icon centres (Finder coordinates, top-left origin) must match between `make_dmg.sh` and `render_background.swift`. Finder needs the disk by its POSIX path for layout, and it removes a volume icon during layout, so the icon is added afterwards.

### Windows

- **App settings** (`AppSettings.cs`). Available under Help > App settings or Ctrl+,. Settings keeps the workspace title-bar height and menu typography, with native Back and navigation buttons; Back restores the existing project workspace. Project Defaults groups new-project preferences under Project Setup, Simulation setup and Calculation. Settings cards group paths and their actions, tool overrides, and notification preferences.
- **Workflow defaults** (`Project.py`, `AppSettings.cs`). Project Defaults also includes ear preparation/modelling and SOFA export. Advanced scan, mesh-grading, calculation and spatial-upsampling preferences start collapsed. Input mode, ear inclusion, bundled model, reusable numerical settings and export options apply through the public `project new-defaults` operation only when creating a project. Imported, duplicated and existing settings remain intact. Input/output artifacts, measured ear distance, microphone placements, scan-specific orientation, crop polygons and saved fit/editor state are excluded; evaluation grid and default project parent remain configurable. The shared operation validates and returns the canonical settings rather than having the client reconstruct project defaults.
- **Mesh2HRTF resources and dependency bundle** (`AppSettings.cs`, `ProjectDocument.cs`). Developer mode can override `paths.mesh2hrtf_path` directly by choosing either the Mesh2HRTF checkout root or its `mesh2hrtf` directory. The choice must contain `Mesh2Input/mesh2input.py`. Resource discovery, prerequisites and relative evaluation-grid resolution use that effective directory. The Python `mesh2hrtf` package used for SOFA processing still belongs to the chosen Python environment; NumCalc retains its own executable override. Mac configuration generation explicitly writes its own environment's resource path so a Windows tool path retained by an imported project cannot take precedence there.
- **External dependencies** remain a useful developer override on both platforms, rather than a separately executable component. The bundle supplies `bin` to the child-process search path and the default `src/Mesh2HRTF/mesh2hrtf` resources. Windows `bin` also contains the PMP, C++, GCC and pthread runtime libraries required by the native mesh grader. Python packages such as Blender, PyMeshLab and PyTorch live in the Python environment, not this bundle. Windows exposes Open alongside Choose and Use default for the dependency folder; an explicit Mesh2HRTF override takes precedence over the bundle's resource directory.
- **Ear editor tools** (`WindowsEarEditor.cs`). Select Faces and Cutting Plane use the same centered native SelectorBar as the manual fitter. Switching tools retains the face selection and plane settings. Cleanup remains outside the tools, matching the Mac editor: Keep Largest Component removes loose fragments from the whole mesh in either mode.
- **Time zone warm-up** (`Sources/Pinna2HRTF.Windows/App.xaml.cs`). `FileInfo` timestamps can lazily initialise `TimeZoneInfo` under a lock. It is initialised before XAML loading and background inspection, because an STA lock wait inside `Loaded` pumps native callbacks into the half-built window.
- **Single instance** (`App.xaml.cs`). A named mutex (`Local\Pinna2HRTF.Instance`) is held for the whole process lifetime. The Inno Setup installer, whose script is not in this repository, uses the same name to detect a running app before install or uninstall. A second launch exits without showing a window.
- **DPI** (`App.xaml.cs`). The process opts into Per-Monitor-V2 DPI awareness, so the unpackaged app renders at the monitor's DPI and Windows does not bitmap-scale it at 125/150/200 %.
- **Title bar** (`WindowChrome.cs`). There is one title-bar contract for the main and editor windows. Layout sizes are DIPs, while Windows reports caption insets in physical pixels, including on mixed-DPI PCs. The Windows 11 non-client frame lies outside the XAML background, so it is themed explicitly through `DwmSetWindowAttribute`. Otherwise the default light frame remains as a thin strip. On Windows 10 the unsupported attributes return an HRESULT and change nothing. Optional diagnostics never prevent a window from opening.
- **Editor windows** (`NativeEditor.cs`). Each native editor is a separate XAML root. It gets its own themed surfaces and follows the main window's theme, including popups.
- **Child processes** (`OwnedProcess.cs`). Each tool joins its own kill-on-close job object before its first instruction runs. Callers pass argument arrays, and `OwnedProcess.Quote` is the only place where Windows quoting happens. Both output readers are observed even when cancellation, launch or the protocol failed.
- **Native load order** (`ScanPreparation._meshlab`). The Windows wheels of MeshLab and Blender share native DLL names. Loading MeshLab first makes the later `bpy` import fail with `ERROR_PROC_NOT_FOUND`, so `bpy` is imported first on win32. Receipt inspection needs neither library.
- **Non-ANSI paths in SOFA I/O** (`HRTFCalculation/SofaIO.py`). libnetcdf's narrow-path check uses the active code page. Names outside that code page are read and written with native Python file I/O and netCDF's in-memory API. No system locale or process working directory is changed.
- **Recycle Bin** (`HRTFCalculation/ShellRecycle.cs`, called from `HRTFCalculation/ProjectTrash.py`; `WindowsProjectSafety.cs`). `FOFX_RECYCLEONDELETE` requests recycling. The progress sink vetoes any delete that lacks recycle semantics or whose folder identity (volume and file index) changed. Completion requires an actual Recycle Bin item. Remote and removable roots are listed only, because safe Shell recycling has not been established for them.
- **Background output scans** (`MainWindow.xaml.cs` `ReconcileOutputsAsync`). A background reconciliation that is not `required` swallows every exception. The outputs may be busy (locked by another window or a running stage) or copied mid-scan, and the next refresh retries. Explicit operations pass `required: true` and report their errors.
- **Touchpad navigation** (`SharedNavigation.cs`). Composition captures Precision Touchpad input only over the viewport, and mouse-wheel messages stay with Helix. No wheel-size or device heuristics and no global input-mode switching are used. Older systems and drivers keep ordinary mouse-compatible navigation. Help sits behind a deliberate Controls flyout, not a hover popup over the mesh.
- **Tooltips** (`MainWindow.xaml.cs`). One stable tooltip instance is kept per button. Replacing it while the status timer refreshes the buttons makes WinUI close a valid hover.
- **Numeric input** (`NumericInput.cs`, `NumberBoxEditing.cs`, `SettingsInput.cs`, `WindowsPPMFitting.cs`). A dot may be an invariant decimal or a localised thousands separator, so grouped spellings are recognised explicitly. Drafts stay out of the saved project until Enter or focus loss. In particular, a rounded automatic distance must never become a manual geometry override, and focusing a value displayed with two decimals must not replace the saved parameter with its rounded display. In the fitter, NumberBox's built-in clear button cancels the current draft and does not clear the value. `TextBox` creates its clear-button template lazily on first focus, and the handler runs after the template's own. An asynchronous mesh measurement may finish while the user is typing and must not overwrite the draft.
- **Offline drives** (`PathIdentity.cs`). An offline drive has no resolvable ancestor. Its absolute spelling is kept for overlap checks, and the selected project validates availability.
- **Sidebar reconciliation** (`Ui3Behavior.cs`). Flattened folder lists are reconciled without removing and reinserting their anchors. Projects that cross a folder boundary are removed first and then inserted below their destination. Status updates and collapse/expand leave folder rows alive.
- **Mac-style layout flavour** (`WindowsMacLayout.cs`). This build flavour changes presentation only. Controls, project models and pipeline services are shared, and the default build keeps its original layout.

### Windows packaging

- `Scripts/build_windows_port.ps1` checks the native payload before replacing a previously working package. WinUI's XAML compiler writes page resources (`*.xbf`, `Pinna2HRTF.pri`) next to the publish folder, so they are copied explicitly for unpackaged, self-contained deployments. The complete sibling runtime of the mesh grader and NumCalc (DLLs and helper tools) is copied, so the portable app also works offline.
- `Scripts/make_windows_runtime_portable.ps1`: CPython's Windows venv launcher embeds a base interpreter path. The portable runtime uses the real interpreter and relative `._pth` files instead, so relocation does not depend on the current directory, a system Python or the original build folder.
- `Scripts/trim_windows_runtime.ps1` ships prebuilt inference, not the C++ extension SDK. Every DLL, Python extension, licence and metadata file is kept, and removal is limited to exact locations.
- `Scripts/prepare_windows_external_tools.ps1`: a fresh MSYS2 installation has `bash` before the UCRT64 packages are installed, so the presence of `bash` alone does not mean the toolchain is ready.
- `HRTFCalculation/RunConfig.py` exports its plots with the `Agg` backend, so the portable CLI needs no Tcl/Tk desktop runtime. The pinned Mesh2HRTF SOFA merger accepts literal file paths internally. `collect_sofa_files` pairs files by name and calls it directly, which bypasses its glob-based directory discovery.
